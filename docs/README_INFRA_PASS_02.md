# Adventure Platform — AWS Infrastructure Pass 02

This pass makes the existing Python application database-portable and provisions the first runnable AWS staging backend.

## What this pass does

- Local app: still uses `data/game_state.sqlite3` automatically.
- AWS app: uses PostgreSQL through the same existing stores.
- Adds RDS PostgreSQL + Secrets Manager.
- Adds one ECS/Fargate backend task + ALB.
- Does **not** deploy React/CloudFront yet.
- Does **not** migrate existing local SQLite records. Staging starts with an empty database.

The patch deliberately does **not** replace `app/main.py`, `app/game/session.py`, or the React source. That protects the newer QTE/micro-event/gameplay work already merged locally.

The backend source changed, so rebuild `staging-current` before deploying ECS:

```bash
cd /Users/prodigitalvr/PERSONAL/OnlineAdventureGame/root
./scripts/aws/package-backend.sh
./scripts/aws/upload-backend-source.sh

```

Stop if CodeBuild does not end with `Backend build: SUCCEEDED`.

## 4. Inspect the new AWS resources before creating them

```bash
./scripts/aws/runtime-diff.sh
```

Expected new classes of resources:

Data stack:
- RDS PostgreSQL instance
- DB subnet group
- generated DB credential secret
- OpenAI API-key secret

Backend stack:
- ECS cluster
- Fargate task definition/service
- task execution IAM policy/roles generated by CDK
- CloudWatch backend log group
- Application Load Balancer
- listener + target group

No CloudFront/S3 React hosting should appear yet.

## 5. Deploy the database first

```bash
./scripts/aws/deploy-data.sh
```

RDS creation can take several minutes. Wait for `AdventurePlatformData-staging` to reach `CREATE_COMPLETE`.

## 6. Put your real OpenAI key into Secrets Manager

```bash
./scripts/aws/set-openai-secret.sh
```

The script prompts for the key with terminal echo disabled, then sends it directly to Secrets Manager. Do not paste the key into chat, source files, CDK config, or the React app.

## 7. Deploy the backend runtime

```bash
./scripts/aws/deploy-backend.sh
```

The first backend task initializes the empty PostgreSQL schema using the existing store initialization paths.

## 8. Prove the remote Python server is alive

```bash
./scripts/aws/backend-health.sh
```

Expected response:

```json
{"status":"ok","version":"0.5.1"}
```

At this point the Python process is running in Fargate, not on the Mac.

## 9. If backend deployment/health fails

Run:

```bash
./scripts/aws/diagnose-backend.sh
```

It prints recent ECS service events and the recent CloudWatch backend log. Do not randomly edit AWS resources in the console; use the exact failure to make the next patch.

## Important staging behavior

- `backendDesiredCount` stays `1`.
- PostgreSQL is private and reachable only from the backend security group.
- Fargate gets a public IP for outbound internet/OpenAI access, but port 8000 accepts traffic only from the ALB security group.
- The ALB endpoint is HTTP for this preflight. Auth-cookie `Secure` is temporarily false only for this pass. CloudFront/HTTPS will turn it back on in the frontend pass.
- Existing local SQLite accounts/Heroes/adventures are **not** copied to RDS. Local development remains unchanged.
